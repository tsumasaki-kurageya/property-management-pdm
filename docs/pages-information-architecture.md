# GitHub Pages 情報設計・編集方針

## 1. 目的

本書は、建物の所有・投資管理、物件・施設運営、維持管理・実行に関する分析成果物を、業務経験のないソフトウェア開発チームが順番に学び、必要な詳細へ遡れるドキュメントサイトへ再編集する基準を定める。

サイト名称は **「建物の所有・運営・維持管理業務ガイド」** とする。サイト全体は建物管理業務を対象とし、ビルメンテナンス（BM）は「維持管理・実行」レイヤーの中核領域として扱う。BM-01〜BM-18・181業務、12横断プロセス、現場作業手順、generated referenceは既存体系を維持する。

## 2. 対象読者と読後目標

主な対象は、業界固有の略語、契約、法定業務、オーナー・AM・PM・FM・BMの違いに馴染みがないチームメンバーである。

読後に次を説明できる状態を目指す。

1. 建物管理業務が所有・投資管理、物件・施設運営、維持管理・実行の三レイヤーで構成されること
2. オーナー、AM、PM、FM、BMが会社名ではなく、目的・管理対象・権限・期間の異なる業務機能であること
3. PMとFMは上下ではなく、目的の異なる並列機能であること
4. 上位の方針・要求・予算がBMの計画・実行へ具体化され、実績・状態・費用・リスクが次の判断へ戻ること
5. BMが清掃・設備・警備だけでなく、営業、契約、計画、報告、請求、改善まで含むこと
6. 業務ID、上位業務領域ID、KPI・KRI、接続種別をどこで調べるか

## 3. 概念階層と学習順序

概念階層は「業務が何に含まれるか」を表す。学習順序は「初学者がどの順番で読むか」を表す。両者を混同しない。

### 3.1 概念階層

```text
所有・運営・維持管理の業務構造
├─ 所有・投資管理
│  ├─ オーナー
│  └─ AM
├─ 物件・施設運営
│  ├─ PM
│  └─ FM
└─ 維持管理・実行
   └─ ビルメンテナンス業務
      ├─ 業務の全体像
      ├─ 現場の業務
      ├─ 異常と周辺業務
      └─ 条件による違い
```

「レイヤー間の接続」と「代表シナリオ」は特定レイヤーへ包含せず、三レイヤーを横断する章として配置する。

### 3.2 推奨学習順序

| 段階 | 読者の問い | 主な章 |
|---|---|---|
| 1. 入口 | このサイトは何を扱い、誰が関わるか | はじめに |
| 2. 全体構造 | 建物管理業務はどのレイヤーで構成されるか | 所有・運営・維持管理の全体構造 |
| 3. 各レイヤー | 各役割は何を目的に、何を判断・実行するか | 所有・投資管理、物件・施設運営、維持管理・実行 |
| 4. BM内部 | BMにはどの仕事があり、どう循環するか | 業務の全体像、現場の業務、異常と周辺業務、条件による違い |
| 5. 接続 | なぜその作業を行い、誰が判断するか | レイヤー間の接続 |
| 6. 適用例 | 実際のテーマで役割間連携をどう追うか | 代表シナリオ |
| 7. 詳細確認 | ID、プロセス、接続、条件をどこで調べるか | リファレンス |

所有・投資管理、物件・施設運営、維持管理・実行は同じ業務レイヤー水準で配置する。深い階層は折りたたみ、初期表示でサイドバーを過密にしない。

## 5. 本文とリファレンスの境界

| 層 | 目的 | 内容 |
|---|---|---|
| 学ぶための本文 | 初学者が全体像から順番に理解する | 平易な説明、代表例、図、要点 |
| 調べるためのリファレンス | ID、条件、詳細定義を追跡する | 181業務、12プロセス、上位接続、重要業務、各種プロファイル |

本文だけで新しい業務定義、KPI・KRI、責任分界、接続関係を追加しない。分析正本を初学者向けに再構成し、網羅的な定義はリファレンスへ分離する。

## 7. 正本と変更順序

上位業務レイヤーの正本は次の4ファイルである。

- `docs/management-structure/roles-and-layers.md`
- `docs/management-structure/business-domains-and-kpis.md`
- `docs/management-structure/decision-and-responsibility.md`
- `docs/management-structure/management-to-bm-map.md`

変更順序は、分析正本、学習用本文、リファレンスとリンク、整合検証の順とする。

## 8. 後方互換性

- 既存URLを変更・削除しない
- 既存ページを新しいパスへ単純移動しない
- `/property-management-pdm` のbase pathを維持する
- 末尾スラッシュを維持する
- 既存アンカーと内部リンクを維持する
- BM-01〜BM-18・181業務、12横断プロセス、generated referenceを別体系へ移動しない
- `/introduction/people-and-roles/` と `/variations/responsibility-boundaries/` のslugを維持する
- 深いサイドバー階層は折りたたむ

## 9. 執筆ルール

- 役割を会社名・固定的な序列として表現しない
- PMとFMを目的の異なる並列機能として示す
- 技術評価、費用査定、承認、実行、確認、検収、法的義務、残存リスク受容を分ける
- BM会社の売上・原価と、物件側OPEX・CAPEX・NOI・NCFを混同しない
- 図だけで完結させず、図の読み方と同内容の表・文章を置く
- 代表例を全案件の必須手順として断定しない
- 個別案件では契約、権限規程、法令、行政運用を優先する

## 10. 検証方針

- サイトタイトルとdescriptionが建物管理業務全体を表す
- 三つの業務レイヤーが同じ水準で認識できる
- BM内部の既存章が維持管理・実行の配下として認識できる
- レイヤー間の接続と代表シナリオが横断章として配置される
- PC・タブレット・モバイルでサイドバーを操作できる
- 折りたたみ状態でも主要ページへ到達できる
- 既存URL、base path、末尾スラッシュ、内部リンクが維持される
- `npm run verify` と `npm run test:e2e` が成功する
- マージ後のDeploy GitHub Pagesと公開後スモークテストが成功する
